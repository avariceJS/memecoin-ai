# Independent Reassessment: Path to Large-Scale Brain
# Claude Opus 5.5 Review — 2026-10-07

After studying the handoff document and all conducted experiments, this is an independent 
assessment of what must change to scale by orders of magnitude.

## Executive Summary

YOU BUILT AN EXCELLENT RESEARCH PROTOTYPE WITH STRONG VERIFICATION, BUT THE ARCHITECTURE 
IS STUCK IN A "BOUNDED CAMPAIGN" PARADIGM.

For true scaling, you need not evolution of the current system, but ARCHITECTURAL MIGRATION 
while preserving the best contracts.

## Main Conclusion

The critical path is DATA PLANE, not because "not enough data," but because:

FUNDAMENTAL PROBLEM: You built a system for BOUNDED CAMPAIGNS, but need a CONTINUOUS DATA PRODUCT.

Current architecture:
  Manual campaign → bounded acquisition → materialize all → cap → train → seal

Needed architecture:
  Continuous ingestion → versioned partitions → streaming snapshots → incremental training

EVIDENCE:
- 965 registry markets → 0 qualified USD training decisions (vacuum)
- 100 hydrated pools → 38 had no support
- 147 RPC calls yielded 1,579 events, but admission yield catastrophically low
- Each experiment is a new manual campaign with new bounds

Target/causal defects are SECONDARY. Yes, there are problems:
- Horizon-median coupling (confirmed)
- Policy-forecast misalignment (entry timing vs forecast interval)
- Calibration (coverage 1.6%/78%/99% instead of 10%/50%/90%)

But EVEN A PERFECT MODEL WON'T HELP if you cannot turn available markets into qualified 
examples with sustained throughput.

### 3. Coherent Two-Mac → Cluster Architecture?

TWO-MAC ARCHITECTURE (keep this pattern):

Mac 1 (Owner/Control):
- Operator/UI/Control Center
- Source coordinator (schedules, budgets, priorities)
- Canonical metadata catalog (SQLite is fine here)
- Paper/Watch runtime
- Release management

Mac 2 (Worker):
- Heavy data processing (acquisition, decoding, features)
- Training jobs (CPU/MPS now, GPU later)
- Offline analysis/ablations
- Evidence generation

Communication:
- Sealed immutable artifacts (already working)
- Manifest-based references (not file copies)
- No shared mutable SQLite
- Job queue via catalog, not distributed locks

NATURAL CLUSTER EXTENSION:

Owner (Mac 1 equivalent):
  - Coordinator/scheduler
  - Metadata catalog
  - UI/API
  - Paper runtime

Workers (Mac 2 → N workers):
  - Acquisition workers (parallel pools/ranges)
  - Feature workers (parallel partitions)
  - Training workers (GPU jobs)
  - Evaluation workers (benchmark scoring)

Storage:
  - Immutable object store (S3/GCS/local)
  - Partitioned by venue/time/schema
  - Manifest catalog (SQLite → Postgres at scale)

WHERE SQLITE/JSON STAYS:

SQLite:
- Coordinator catalog (pools, coverage, budgets)
- Job queue and status
- Manifest registry
- Paper ledger (per-book, not global)
- Local worker state

JSON:
- Manifests (small, human-readable)
- Receipts/evidence
- Configuration
- API responses

WHERE TO REPLACE:

Replace JSON with columnar:
- Raw RPC responses (Parquet/Arrow)
- Decoded events (Parquet)
- Features/labels (Parquet/HDF5)
- Training batches (memory-mapped tensors)

Replace full materialization:
- Snapshot = manifest + partition refs
- Streaming loader with LRU cache
- Incremental feature computation
- Lazy label hydration

### 6. Backbone Change Now, or Objective/Optimization First?

OBJECTIVE/OPTIMIZATION/TARGETS FIRST. STRONGLY.

EVIDENCE FROM YOUR ABLATIONS:

1. Sampling (causal): -11.91% test loss just from fixing sampling
2. Budget: -20.76% test loss from 1k→4k updates
3. LR: Median coverage SD -54.70% (train stability)
4. Clipping: 100% of updates clipped, mean norm 55-96

THESE ARE HUGE EFFECTS. Much larger than typical architecture changes.

CURRENT GRU (2,174 params) IS FINE FOR NOW because:
- You have ~100k decisions (not millions)
- Effective N after sampling is ~1,172
- Bottleneck is optimization, not capacity
- Ablations show clear optimization issues

WHAT TO FIX FIRST:

1. Objective: Define target population weighting explicitly
2. Sampler: Implement importance sampling with stable weights
3. Optimization: LR schedule, gradient clipping threshold, warmup
4. Calibration: Separate calibrator head, proper uncertainty
5. Targets: Policy-aligned intervals, test abstention

THEN MEASURE DATA/COMPUTE CURVES:

Fixed architecture, vary:
  - Training examples: 10k, 50k, 100k, 500k, 1M
  - Updates: 1k, 4k, 16k, 64k
  - Context: 4, 8, 16, 32 bars

If curves plateau → increase capacity
If curves rising → get more data

TRANSFERABLE CAUSAL RESULTS:
- Sampling effect is real and large
- Budget matters (but 4k is not optimal)
- Optimization is unstable
- Calibration is broken

NOT TRANSFERABLE:
- Exact numbers (different data)
- 16.64% as target (that was capped intervention)
- Horizon head fix (structural, but not calibration fix)

## Implementation Failures (Not External Limits)

- Early indexed Alchemy request omitted maxSupportedTransactionVersion=0, failed with -32015
  (request bug, corrected indexed history later worked)

- Raw audit hit 600s deadline from repeated scans across 264,529 versions
  (adding index (pin, open_s) reduced audit batch to 2.235s, full to 8.051s)
  (access pattern fix, not GPU need)

- .DS_Store caused paper failure while source healthy
  (recovery and health dimensions had to be separated)

- Substring-based consumer guard could misclassify expired legacy supervisors
  (later exact-role/hash diagnostics passed finite suffix run)

Final 31-GET suffix: 927.4s at >=30.316s spacing, all HTTP 200, zero unknown consumers.
This qualifies that finite envelope, not ceiling of Alchemy throughput.

Six hot pools, universe 24, 48k train cap, short windows, CPU1, 1,000 updates, expiry, 
manually approved campaigns were PILOT BOUNDS, not hardware or provider limits.

LARGER ORGANIZATIONAL ERROR: Evolving acquisition as isolated campaigns instead of 
continuous data product with coverage SLO, durable backlog, shared budget, owner, and 
research namespace.

## Proposed Direction (Not Approved Migration)

DATA PLANE:

1. Continuous raw ingestion with separate live/backfill priority, account-level provider 
   coordinator, actual attempt/rate/CU budgets, leases, deadlines, classified retries

2. Durable coverage ledger by venue/pool/mint/time: wanted, fetched, decoded, qualified, 
   feature-ready, label-ready, gaps/reasons. Measure useful episodes as well as bytes/RPC

3. Immutable raw plus versioned canonical events, partitions by chain/venue/time/schema, 
   idempotency, finality/reorg rules, per-partition quarantine

4. Shared research/runtime feature semantics, explicit availability, multi-resolution 
   bars/events, valid USD conversion, dependency manifests. Separate raw retention from 
   training/execution admission

5. Immutable snapshots referencing partitions/transforms instead of nested JSON; streaming 
   batches, cached tensors, train-only transforms, explicit objective/draw schedule

LEARNING/EVALUATION PLANE:

Version recipes by target population, exposure/compute budget, model, optimizer/sampler, 
checkpoint rule, seeds, validation role. Record unique draws, cohort/day exposure, 
gradients/updates, actual compute. Build permanent development/calibration/prospective 
data roles and exposure log. Preserve traffic weighting, strata, failure denominators, 
empirical/linear/champion baselines. Scale representation/compute only with learning 
curves; size/FLOPs are axes, not outcomes.

CONTROL PLANE:

Isolated source, feature, training, evaluation, and paper workers with shared resource 
leases and immutable references. Mac1 may remain operator/UI and Mac2 research/data/training 
worker. Scheduler must account for RAM/IO/accelerator contention. Process scans are 
diagnostics, not distributed locks. Unknown consumers should generate identifiable redacted 
incidents; retries require classified transient causes and budgets. Promotion/release 
remain separate from job completion.

LLMs:

Strong external models can review bounded code/evidence; not necessarily MCP services and 
must not be given secrets. Local Qwen3.5 35B on 48GB Mac is free preprocessing worker for 
redacted log triage, clustering, summaries, structured annotations with source references. 
Reported ~47 tok/s with substantial swap was not re-benchmarked. Qwen output is not ground 
truth, promotion authority, or market feature without independent experiment. Scheduler 
should yield memory to heavy training; do not use model just to justify residency. No LLM 
belongs in trading runtime.

## What I Would Do If Starting Again

Keep ambition for large Brain from day one and treat market-data platform, learning/evaluation, 
and paper/operator experience as peer products. Start with one complete supported 
source-to-example path: durable raw acquisition, versioned decoding, identity, 
availability-aware prices, feature/target dependency, coverage ledger, streaming snapshots. 
Design schemas and partitions for millions of examples rather than Python dictionaries in RAM.

Build broad development and future evaluation in parallel with first continuous corpus. 
Define AUTO/Watch estimands and denominators, temporal and mint-disjoint cohorts, separate 
calibration role before model iteration. Keep empirical/linear as transparent champions; 
use small GRU to prove learning plumbing, not to declare generation after seconds-long fit. 
Then measure data/compute scaling and increase model representation where broad development 
shows benefit; move to GPU when pipeline shape and utilization justify it.

Record sampler objective, unique exposure, gradient/clipping/update diagnostics, per-horizon 
calibration, checkpoint variability from first recipe. Do not treat equal-pool sampling as 
neutral or head flexibility as calibration. Make acquisition continuously managed service 
with account-wide budgets, classified retries, backpressure, partition quarantine, coverage 
SLOs; use bounded qualification to validate it, not as substitute for it. Keep STOP, 
receipts, financial boundaries.

Bring Watch Market to accepted end-to-end owner-host scenario early: concrete mint, explicit 
supported/unsupported behavior, pinned champion, visible forecasts, isolated book. Carry 
forward contracts, provenance, immutable artifacts, causal replay, accounting, useful 
decoders, independent verification. Rewrite where pilot caps, JSON materialization, manual 
campaign-specific guards hardened into architecture; do not rewrite everything for fashion 
or buy compute as substitute for data and benchmark discipline.

MOST IMPORTANT CHANGE IN APPROACH: Measure progress by sustained growth in useful incoming 
experience and independent evidence that Brain learns better from it. Verifiability should 
make that growth reliable, not replace it.
