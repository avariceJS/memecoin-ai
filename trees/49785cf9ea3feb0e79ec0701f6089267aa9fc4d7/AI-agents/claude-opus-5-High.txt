0. HEADLINE VERDICT
================================================================================

The handoff is unusually honest and factually accurate. I could not find a
materially false claim in it. But its diagnosis is too generous in one place
and too harsh in another.

TOO GENEROUS: it frames the problem as "incomplete data plane + weak benchmark
breadth + underspecified objective." True, but it misses that the system
contains a HARD 7-DAY TRAINING WINDOW that makes corpus growth structurally
impossible. That is not a data plane gap. It is a design decision that caps
lifetime learning regardless of how much data is acquired.

TOO HARSH: it treats the verification/provenance machinery as a cost to be
defended. It is actually the most valuable asset in the repository and the
hardest thing to rebuild.

ONE-LINE VERDICT:
  You have built an excellent laboratory notebook around a learning system
  that is structurally forbidden from learning. Keep the notebook. Redesign
  the learning system.

1. WHAT IS FUNDAMENTALLY WRONG
================================================================================

--------------------------------------------------------------------------------
1.1 THE CORPUS CANNOT GROW - single most important finding
--------------------------------------------------------------------------------

Evidence: src/memecoin_paper/service.py:39-46

    def source_rows(c, cutoff, training=False):
        if c.get("source_backend") == "continuous":
            from memecoin_continuous.store import view
            return view(
                Path(c["source"]), cutoff,
                since=cutoff // 10**9 - (7 if training else 2) * 86400
            )

Training reads ONLY THE LAST 7 DAYS of bars.

Corroborated independently in src/memecoin_curriculum/archive.py:27-37, which
caps to 7 days and then to 28,000 bars, with the explicit comment:
    "Match deployed source_rows(training=True) and service.training without
     changing it."

CONSEQUENCE, stated plainly:
Every training run sees a fixed-size sliding window. Acquiring 10x or 1000x
more data changes nothing about what the model learns from, because data older
than 7 days is never read by the trainer. The system is not accumulating
experience. It is continuously forgetting it.

This reframes the whole project. The handoff's "the main bottleneck is the data
plane" is understated. There is no data ACQUISITION bottleneck that more
Alchemy throughput fixes. There is a data RETENTION AND CONSUMPTION bottleneck.
Fixing acquisition without fixing this produces more captures the learner never
reads.

RATING: Fundamentally wrong. Highest priority.

--------------------------------------------------------------------------------
1.2 THE EVALUATION WINDOW IS 3 HOURS, AND MORE DATA CANNOT FIX IT
--------------------------------------------------------------------------------

Evidence: src/memecoin_operator/learning.py:61-69

    end = cutoff // NS // 300 * 300
    bounds = dict(
        train_end_s      = end - 21600,   #  6 hours
        validation_end_s = end - 10800,   #  3 hours
        test_end_s       = end,           #  3 hours
    )

Train 6h, validation 3h, test 3h. This is why the test set is 249 decisions on
8 pools over one UTC day. Not an accident of sparse data - the DESIGNED split.

Three structural consequences; the third appears to have been missed:

  (a) No seasonality, regime, or day-of-week variation is observable
      even in principle.

  (b) Any result on a 3-hour window is dominated by whatever regime
      happened that particular afternoon.

  (c) MOST IMPORTANT: validation and test are drawn from IMMEDIATELY
      ADJACENT 3-hour blocks of the same day. Selecting a checkpoint on
      validation and reporting on test is close to selecting and reporting
      on the same experiment. The "no leakage" audits are correct about
      bytes and timestamps, and the generalization claim is still weak.
      Hash seals protect against contamination, not against a split design
      that makes both folds nearly the same regime.

This defect is INDEPENDENT of 1.1. Even with unlimited retained data, this
split still yields a 3-hour test.

RATING: Fundamentally wrong.

--------------------------------------------------------------------------------
1.3 THE TRAINING OBJECTIVE IS DISCONNECTED FROM THE DECISION RULE
--------------------------------------------------------------------------------

This is the defect most underweighted in the handoff, which lists
"cohort/objective mismatch" as one contributor among several. I consider it a
primary cause of the system producing nothing economically meaningful.

Evidence:
  - Loss: src/memecoin_ml/training.py:117-131 - pinball loss over the WHOLE
    return distribution. Implementation is correct.
  - Decision: src/memecoin_paper/engine.py:186

        elif q[1] <= math.log(1.016):
            reason = "median_below_cost_buffer"

    Entry only when median forecast > +1.6% per 5-minute bar.
    Plus rejection when q[0] < -0.25 (predicted tail risk).

So training optimizes average accuracy across all bars - overwhelmingly tiny
moves near zero - while the decision rule only ever fires in the extreme right
tail. Nearly all gradient signal is spent on a region the policy never acts on.

The measured numbers confirm this is not theoretical:

    GRU test coverage:  q10 = 1.606%   q50 = 77.912%   q90 = 98.996%
    Nominal:            q10 = 10%      q50 = 50%       q90 = 90%

A q50 with 78% coverage means the predicted median sits well above the realized
median, while the tails have collapsed inward (q10 at 1.6%, q90 at 99%). The
model has learned a narrow, badly located distribution. With intervals that
degenerate, the "q50 > 1.6%" gate becomes close to a coin flip on a
miscalibrated statistic - exactly the observed "many intents, zero fills" /
"two trades" behavior.

THE 1.6% THRESHOLD IS ALSO NOT FREE:
  src/memecoin_paper/engine.py:9  ->  FEE, SLIP = 0.0025, 0.005
  50bps slippage + 25bps fee per side = ~150bps round trip.

The threshold is a hardcoded constant sitting just above assumed costs. It was
never derived from a calibrated cost model nor optimized jointly with the
forecaster. Result: an uncalibrated threshold applied to an uncalibrated
quantile.

RATING: Fundamentally wrong. Trading quality is not reachable by improving
pinball loss on this objective.

--------------------------------------------------------------------------------
1.4 THE FEATURE SPACE IS TOO IMPOVERISHED FOR THE STATED AMBITION
--------------------------------------------------------------------------------

Evidence: src/memecoin_brain/data.py:16-29

    FEATURES = (log_return_1, log_close_open, log_high_low, log_volume_usd,
                upper_wick, lower_wick, volume_vs_past, log_return_3,
                log_return_6, past_return_rms, past_positive_fraction,
                zero_volume)

12 scalars, all derived from a single pool's own 5-minute OHLCV.

ABSENT: cross-sectional / market-wide context, liquidity and depth, holder
concentration, trade-level microstructure, buy/sell imbalance, creator/deployer
history, pool age at decision time, SOL/USD regime, any on-chain signal at all.

This matters more than it appears. Raw Solana transactions are being ingested
(src/memecoin_pumpswap, 3,078 lines of decoder) and then nearly all of that
information is DISCARDED to produce 12 numbers per bar from a GeckoTerminal
price series. The handoff notes the raw lane "added zero qualified USD training
decisions." Sharper statement: the raw lane is currently a parallel system that
does not feed the learner at all.

For memecoins specifically - where returns are driven by liquidity events,
holder concentration and deployer behavior - a 12-feature univariate price
summary is close to the weakest possible representation.

THIS, NOT GRU WIDTH, IS THE BINDING CAPACITY CONSTRAINT. I agree with the
handoff that a backbone change is unjustified today, but for a stronger reason
than it gives: with 12 univariate features there is almost nothing for a larger
model to learn.

RATING: Fundamentally wrong (representation).

--------------------------------------------------------------------------------
1.5 ACQUISITION LEDGER: QUADRATIC COST AND SILENT WORK LOSS
--------------------------------------------------------------------------------

Two separate defects.

(A) QUADRATIC LEDGER

src/memecoin_runner/ledger.py:68-83 - Ledger.audit() re-reads, re-parses and
re-hashes EVERY event file on construction.

src/memecoin_continuous/source.py:212, 282-289 - fetch() appends two events per
request, each embedding a FULL COPY OF THE SCHEDULER STATE FOR ALL POOLS:

    ledger.append("reserved", job=job, state=s, capture=...)
    ...
    ledger.append("outcome", job=job, state=s, status=status, ...)

Cost grows as O(requests x pools) in disk and O(events) re-hashed per tick.
Invisible at pilot scale (hundreds of requests, 24 pools). Fatal at target
scale.

Related full-scan hotspots:
  - src/memecoin_brain/source.py:88   host_guard() does root.rglob("*") over
                                      every capture on each guard call.
  - src/memecoin_continuous/store.py:172  audit() re-verifies the entire corpus
                                      from disk.

(B) PERMANENT GAP DEBT - THIS IS A CORRECTNESS BUG

src/memecoin_continuous/source.py:119-122

    else:
        q["history_pages"] += 1
        q["history_done"] = True  # failure/crash never retries this history page

history_done is set at RESERVATION, before the request is issued. A timeout, a
429, or a crash PERMANENTLY ENDS BACKFILL for that pool. Combined with the
history_pages < 30 bound (source.py:93), backfill is capped at 30 pages/pool
and any failure truncates it early and irreversibly.

This is the mechanical explanation for the handoff's "historical pages often
stopped at caps, not coverage completion; durable gap debt and resumable
pagination remain weak." It is not weak - it is BY CONSTRUCTION, and it is a
correctness bug, not merely a scale limit.

IMPLICATION: current coverage statistics silently understate what was actually
available from the provider.

RATING: Fundamentally wrong (A = scale, B = correctness bug).

--------------------------------------------------------------------------------
1.6 THROUGHPUT: ~1 REQUEST / 12s, SINGLE-THREADED, SINGLE-PROVIDER
--------------------------------------------------------------------------------

Evidence:
  src/memecoin_continuous/source.py:176-180  fetch() sleeps to enforce
      request_spacing_s (default 12)
  src/memecoin_continuous/source.py:296-326  tick() does at most 8 sequential

CRITICAL: the qualified USD path depends entirely on GeckoTerminal

IMPLICATION: buying more Alchemy throughput today would change nothing. The
constraint is architectural, not commercial. The handoff says this ("much of
that campaign was GeckoTerminal rather than Alchemy"); the implication deserves
emphasis.

RATING: Fundamentally wrong (architecture), though commercially harmless today.

--------------------------------------------------------------------------------
DISAGREEMENT WITH THE HANDOFF ON SEQUENCING (items 3 and 11)
--------------------------------------------------------------------------------

The handoff suggests an LR x clipping factorial as "the most informative next
short ML diagnostic suggested by current evidence."

I DISAGREE.

Those diagnostics, and the horizon-head fix, would optimize a model that is:
    (a) trained on 7 days of data,
    (b) evaluated on 3 hours,
    (c) against an objective disconnected from the decision rule,
    (d) using 12 univariate features.

Every such result would be measured on the exposed 86-pool snapshot and would
not transfer.

The clipping observation IS interesting evidence of optimization pathology -
100% of updates clipped, pre-clip norms 55.3-95.9 against threshold 1, meaning
the EFFECTIVE LEARNING RATE IS SET BY THE CLIP, not by the LR setting. But
diagnosing the optimizer of the wrong objective on the wrong data is premature.

Fix 1.1 through 1.4 first. Several of these pathologies may not survive the fix.

Verified code basis for the horizon-head defect (it is real):
    src/memecoin_ml/models.py:55-92 - horizon enters only via the concatenated
    action vector at the final shared nn.Linear head, so
    median(15m) - median(5m) is a history-independent constant.
    Confirmed structurally; priority is nonetheless low.

================================================================================
5. THE CORRECT DIRECTION
================================================================================

--------------------------------------------------------------------------------
PHASE 1 - MAKE LEARNING POSSIBLE (prerequisite for everything else)
--------------------------------------------------------------------------------

 1. REMOVE THE 7-DAY WINDOW. Training reads the full retained corpus.
    This alone changes the system's nature from forgetting to accumulating.

 2. REDESIGN SPLITS TO BE TIME-SCALED, NOT HOUR-SCALED:
    multi-week/month train, multi-day validation, a SEALED NEVER-REUSED
    multi-day test, plus a SEPARATE CALIBRATION BLOCK.
    Mint-disjoint as well as time-disjoint folds.

 3. WIRE IN THE EXISTING STREAMING LOADER. The work is already done in
    src/memecoin_curriculum/streaming.py.

 4. FIX THE LEDGER (snapshot + compaction; stop embedding full state per
    event) AND THE history_done BUG. Until the latter is fixed, every
    coverage number produced understates reality.

--------------------------------------------------------------------------------
PHASE 2 - MAKE THE DATA WORTH LEARNING FROM
--------------------------------------------------------------------------------

 5. PARALLEL, MULTI-PROVIDER ACQUISITION with a shared budget coordinator,
    classified retries, and a DURABLE COVERAGE LEDGER:
        wanted / fetched / decoded / qualified / feature-ready / label-ready
        + explicit gap reasons
    Measure USEFUL EPISODES, not HTTP 200s.

 6. CONNECT THE RAW ON-CHAIN LANE TO THE LEARNER.
    PumpSwap is already decoded. Surface liquidity, trade imbalance,
    holder/deployer features. This is where the real alpha lives and it is
    the highest-leverage use of paid Alchemy capacity.

 7. PARTITIONED COLUMNAR STORAGE (Parquet by chain/venue/date) with immutable
    raw retained. Keep SQLite as catalog/control plane.

--------------------------------------------------------------------------------
PHASE 3 - MAKE EVALUATION HONEST AND DECISION-RELEVANT
--------------------------------------------------------------------------------

 8. ALIGN OBJECTIVE WITH DECISION. Either:
      (a) train on the policy-relevant event - P(return > cost threshold),
          or expected costed PnL at the executed horizon and interval; or
      (b) keep the quantile forecaster and add a SEPARATELY-FIT CALIBRATION
          LAYER on a dedicated calibration block,
    with the threshold DERIVED FROM A COST MODEL rather than hardcoded at 1.6%.

 9. REPORT CALIBRATION AS A FIRST-CLASS METRIC - signed coverage residuals per
    horizon, interval width, tail behavior - with uncertainty from paired
    mint/time blocks. Pooled pinball alone is what allowed a model with
    1.6/78/99% coverage to look merely "worse by 42%."

10. KEEP EMPIRICAL/LINEAR AS CHAMPIONS until a learned model wins on a broad,
    prospective, never-tuned-against benchmark.

--------------------------------------------------------------------------------
PHASE 4 - SCALE ONLY WHEN JUSTIFIED
--------------------------------------------------------------------------------

11. Expand features and model capacity ONLY WHERE LEARNING CURVES SHOW BENEFIT.
    Move to GPU when the pipeline can actually saturate it.
    Size and FLOPs are axes, not outcomes.

--------------------------------------------------------------------------------
ON V1 / V2 / V3
--------------------------------------------------------------------------------

Define generations by:
    - retained corpus SPAN and BREADTH
    - qualified-episode THROUGHPUT
    - benchmark SUPPORT
    - CALIBRATION quality

NEVER by a new weights hash. A generation that trains on more days of more
markets and holds calibration is progress. One that only changes a hash is not.

--------------------------------------------------------------------------------
ON THE TWO-MAC -> CLUSTER PATH
--------------------------------------------------------------------------------

WHAT TRANSFERS:
    immutable artifacts + content-addressed references + stateless workers
    + a catalog.
    This is already present conceptually.

WHAT DOES NOT TRANSFER:
    - flock-based single-writer locking
    - whole-file JSON datasets
    - per-event full state copies
    - process-scan guards

Replace those four and the same architecture runs on one Mac or a hundred
nodes.

================================================================================
6. DIRECT ANSWERS
================================================================================

WHAT IS FUNDAMENTALLY WRONG:
    The 7-day training window; the 3-hour evaluation window; the
    objective/decision mismatch; the 12-feature univariate representation;
    the quadratic-and-lossy acquisition ledger.

WHAT IS MERELY UNFINISHED:
    Streaming integration; GPU path; Watch Market acceptance; prospective
    benchmark population; venue coverage; arbitrary numeric caps.

WHAT TO PRESERVE:
    Temporal/causal contracts; immutable captures with first-observed
    versioning; hash-chained provenance; maturity purging; Decimal
    accounting; the decoders; and above all the intellectual honesty of
    the reporting.

WHAT TO REDESIGN:
    The eleven items in section 4 - with DATA RETENTION, SPLIT DESIGN, and
    OBJECTIVE ALIGNMENT strictly before any model or optimizer work.

CORRECT DIRECTION:
    Stop treating this as an ML tuning problem. It is a DATA RETENTION AND
    OBJECTIVE DESIGN problem wearing an ML costume.

    The model is small because the data is small.
    The data is small because the trainer only reads 7 days.
    The results are uninformative because the test is 3 hours and the
    objective does not match the decision.

    Fix those four and the existing verification machinery becomes exactly
    what is needed to scale honestly. Fix them in the other order and you
    will have scaled the failure modes - which is the one genuinely sharp
    warning in the handoff, and it is correct.

================================================================================
7. NOTE ON THE HANDOFF ITSELF
================================================================================

The instruction was not to inherit its conclusions. Having checked them against
code, I found the handoff accurate and unusually free of self-justification.
That is a real asset and reflects well on the process that produced it.

My disagreements are about EMPHASIS AND SEQUENCING, not facts:

  1. It understates the 7-day training window - the system's defining
     constraint, and arguably not surfaced at all as a first-class finding.
  2. It understates the objective/decision mismatch, listing it as one
     contributor among several rather than a primary cause.
  3. It recommends an optimizer diagnostic (LR x clipping factorial) that
     I believe is premature by two phases.
  4. It undersells its own streaming/memmap loader, which is better than
     the "not the B13 path" framing suggests.
